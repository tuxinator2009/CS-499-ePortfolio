Algorithms and Data Structures

The second enhancement to the Travlr Getaways application focuses on improving trip discovery through search, filtering, relevance ranking, and sorting.

In the original application, the trip listing endpoint retrieved the complete collection using an unfiltered database query. This behavior was sufficient for the small dataset used in the original CS 465 project, but it did not provide a useful mechanism for locating or prioritizing trips as the collection grew.

This enhancement introduces an algorithmic processing pipeline that accepts optional search criteria, narrows candidate results, evaluates those results, and returns an ordered set of trips. The implementation demonstrates not only working algorithms, but also the trade-offs involved in deciding where data processing should occur.

The enhanced implementation treats trip discovery as a sequence of data-processing operations. Each stage has a defined responsibility and can be evaluated or modified independently.

Search and Filtering

The enhanced API accepts optional query parameters that allow callers to narrow the trip collection according to useful characteristics rather than always retrieving an undifferentiated list.

Keyword Search

Keyword search evaluates relevant trip information and allows matching trips to be identified from textual search criteria.

Resort Filtering

Trips can be narrowed according to resort information, allowing a caller to retrieve packages associated with a particular destination or resort.

Price Range Filtering

Minimum and maximum price criteria are converted into numeric values and used to eliminate trips outside the requested range.

Duration Filtering

The algorithm extracts the number of nights from the existing human-readable trip duration and uses the resulting numeric value for comparison.

Sorting

Results can be ordered according to supported sort options, including numeric price ordering. Invalid sort options are rejected rather than silently producing unpredictable behavior.

Relevance Ranking

Keyword results receive relevance scores so that stronger matches can be presented before weaker matches. Exact identifying matches receive greater weight than less-specific textual matches.

Algorithmic Design

A major design consideration was deciding whether search operations should occur entirely in MongoDB, entirely in the application, or through a combination of both.

Performing all processing in memory would provide considerable flexibility, but it would require retrieving unnecessary records as the dataset grows. Performing every operation in MongoDB could reduce transferred data, but would make custom relevance scoring and application-specific ranking behavior more tightly coupled to the database query.

The enhancement therefore uses a hybrid strategy. Operations that can efficiently reduce the candidate set can be handled during data retrieval, while application-level processing can perform transformations, relevance scoring, and ordering where greater flexibility is useful.

This separation also fits naturally into the layered architecture introduced during the software engineering enhancement. The repository is responsible for data access, while the service and algorithmic logic can determine how retrieved data should be interpreted and prioritized.

Data Structures and Processing

Trip records are processed as arrays of structured objects. Intermediate values such as parsed prices, extracted durations, normalized search terms, and relevance scores allow the application to compare values according to their meaning instead of relying on their original display-oriented string representations.

This distinction is particularly important for price and duration. In the original data model, perPerson is stored as a string and length contains descriptive text such as 4 nights / 5 days. Helper functions convert these representations into numeric values when algorithmic comparisons are required.

Separating normalization from ranking also keeps the algorithm easier to reason about. Data is first converted into a predictable form, then filtered, scored, and sorted according to the requested criteria.

Complexity and Trade-Offs

For a candidate set containing n trips and k unique search tokens, filtering and relevance scoring require approximately O(n × k) time because each candidate may be evaluated against the normalized search terms.

Sorting the resulting candidate collection requires approximately O(n log n) time using the runtime's comparison-based array sorting behavior. The overall processing cost can therefore be expressed approximately as: 

O(n × k + n log n)

For the relatively small Travlr dataset, this cost is modest. More importantly, the design provides a clear path for scaling. Database filtering and indexes can reduce the number of candidates represented by n before application-level ranking occurs.

This demonstrates an important algorithmic trade-off: the goal is not simply to minimize theoretical complexity in isolation, but to select an approach appropriate to the size of the data, the flexibility required by the application, and the responsibilities of each architectural layer.

Validation and Defensive Processing

Search parameters are treated as untrusted input. The enhancement validates values before applying them to the algorithm and returns meaningful errors when the requested operation is invalid.

For example, a minimum price greater than the maximum price is rejected with an INVALID_PRICE_RANGE response rather than producing misleading results. Unsupported sorting values similarly return an INVALID_SORT_OPTION response.

These checks improve both algorithmic correctness and API reliability because invalid states are detected explicitly rather than being allowed to propagate through the processing pipeline.

Enhancement Narrative

Artifact Description

The artifact used for this enhancement is the Travlr Getaways full-stack web application originally developed during CS 465: Full Stack Development. The application provides a customer-facing travel website, an Angular administrative interface, an Express and Node.js API, and MongoDB persistence through Mongoose.

The original application could retrieve and display travel packages, but its trip retrieval behavior was intentionally simple. The API returned the complete trip collection, leaving no mechanism for searching, filtering, ranking, or sorting results.

Justification for Inclusion

I selected this artifact for the algorithms and data structures category because its original trip retrieval behavior provided a clear opportunity to transform a basic data-access operation into a more useful discovery system.

The enhancement adds search criteria, numeric and textual filtering, relevance scoring, and sorting. It also required converting display-oriented values into representations more appropriate for computation. Prices stored as strings are parsed into numeric values, while descriptive duration strings are interpreted to obtain the number of nights.

The ranking process demonstrates algorithmic decision making by assigning different weights to different kinds of matches. Exact identifying matches can therefore be prioritized over broader textual matches rather than treating every match as equally significant.

The enhancement also demonstrates evaluation of design trade-offs. Search and filtering could have been implemented entirely in the Angular client, entirely in MongoDB, or entirely in server-side memory. Instead, I designed the solution so that data-access concerns and flexible application-level processing could remain appropriately separated.

Course Outcome Alignment

This enhancement most directly demonstrates the program outcome requiring the design and evaluation of computing solutions using algorithmic principles and computer science practices while managing trade-offs involved in design choices.

The enhancement required consideration of search behavior, filtering order, data representation, ranking, sorting, computational complexity, and the division of responsibility between database queries and in-memory processing.

It also supports the outcome involving computing practices that deliver value. A trip catalog becomes substantially more useful when users can narrow and order its contents according to their needs rather than manually examining every available record.

Input validation and explicit handling of unsupported query combinations additionally contribute to the security and defensive-programming outcome by treating externally supplied parameters as untrusted data.

Reflection

One of the most important lessons from this enhancement was that algorithm design in an application is not limited to selecting a textbook data structure or implementing a sorting routine from scratch. The larger problem is deciding how data should move through a system, where each operation should occur, and what trade-offs are appropriate for the expected workload.

The original data model also demonstrated how representation choices affect later algorithms. Values such as price and duration were originally designed primarily for display. Performing useful comparisons required first translating those values into numeric representations. This reinforced the relationship between data modeling and algorithm design.

Another useful part of the process was separating the algorithmic behavior into independently testable functions. Testing price parsing, duration extraction, relevance scoring, filtering, and sorting individually made it easier to verify correctness before testing the behavior through the complete API.

The final implementation passed all five automated algorithm tests and produced the expected results when exercised through direct API requests. The result is a more capable application and a stronger demonstration of how algorithmic principles can solve practical problems in full-stack software.
