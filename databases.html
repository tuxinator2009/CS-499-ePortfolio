Databases

The final enhancement to the Travlr Getaways application focuses on expanding the MongoDB data model from basic trip management into a more complete reservation system.

Before this enhancement, the application stored users and trip records but did not represent customer bookings, ownership of reservation data, historical pricing, or administrative reporting. The database enhancement adds these capabilities while preserving the layered architecture established during the earlier software engineering milestone.

The completed design demonstrates MongoDB document modeling, relationships between collections, schema validation, indexing, aggregation, historical data preservation, role-based access, and resource-level authorization.

Booking and Reservation Model

The new booking collection represents the relationship between an authenticated customer and a selected trip. Each booking contains a unique public booking code, user and trip references, traveler count, booking date, travel date, status, price per person, and total price.

User Relationship

Each booking stores a MongoDB ObjectId referencing the user who created the reservation. This supports customer-specific retrieval and ownership checks.

Trip Relationship

Each booking also references the selected trip, allowing current trip information to be populated when reservation data is displayed.

Historical Snapshot

Selected trip information is copied into the booking at creation time, including trip code, trip name, travel date, and price per person.

Calculated Total

The reservation service calculates the total booking price using the number of travelers and the price in effect when the reservation is created.

Historical Data Integrity

One of the most important database design decisions involved balancing references against historical accuracy.

Storing only a reference to the current trip would reduce duplicated values, but it would create an important problem: changes to a trip after a reservation was created could alter the apparent details of an older booking.

For example, if the current trip price changes from $799 to $999, an existing customer's historical reservation should not suddenly appear to have been made at the new price.

The enhanced design therefore uses a hybrid model. ObjectId references preserve the relationship to the current user and trip documents, while selected booking-time values are stored directly in the booking document.

This approach introduces limited intentional duplication in exchange for more accurate historical records.

Schema Validation

Mongoose schema validation is used to enforce important constraints at the persistence layer.

  • Booking codes are required and unique.
  • User and trip references are required.
  • Traveler counts must fall within the permitted range.
  • Booking status is limited to accepted values.
  • Price values cannot be negative.
  • Travel dates are required, while booking dates are automatically recorded when reservations are created.
  • Automatic timestamps record document creation and updates.

Performing validation at multiple layers helps ensure that malformed data cannot easily reach persistent storage even if one part of the application fails to reject it earlier.

Indexing Strategy

The booking schema includes indexes designed around the access patterns introduced by the reservation system.

Unique Booking Code

A unique index ensures that each public booking identifier maps to one reservation.

User and Booking Date

A compound index on user ID and booking date supports efficient retrieval of an individual customer's booking history in chronological order.

Trip and Status

A compound index on trip ID and booking status supports trip-level queries and administrative reporting.

Status and Booking Date

A compound index on status and booking date supports chronological analysis of confirmed or cancelled reservations.

Security and Authorization

Adding customer-specific reservation data also expanded the security requirements of the application. A user possessing a valid authentication token should not automatically be allowed to retrieve every booking in the system.

Customer Ownership

Booking queries use the authenticated user's ID to return only reservations associated with that account.

Resource-Level Authorization

When an individual booking is requested, the service verifies that the authenticated customer owns the reservation before returning it.

Role-Based Access

User accounts now distinguish between customer and administrator roles. Administrative operations require the appropriate role in addition to authentication.

Privilege Protection

Public account registration explicitly creates customer accounts rather than trusting a role supplied by the requesting client.

These controls address a common class of authorization vulnerabilities in which an authenticated user attempts to access another user's resource simply by changing an identifier in a request.

Administrative Decision Support

The aggregation report also contributes to the Computer Science program outcome involving organizational decision making.

Raw booking documents are useful for individual transactions, but aggregated information provides a different kind of value. Booking count, traveler volume, and estimated revenue can help administrators identify which trips are receiving the greatest demand and compare performance across available packages.

Presenting this information through a dedicated administrative view demonstrates how database design can support both operational functionality and higher-level decision making.

Enhancement Narrative

Artifact Description

The artifact selected for this enhancement is the Travlr Getaways full-stack web application originally developed in CS 465: Full Stack Development. The application includes an Angular interface, Express and Node.js API, MongoDB persistence through Mongoose, authentication, and travel-package management.

Before the database enhancement, the application stored users and trips but did not support customer reservations, ownership of booking records, historical transaction information, or administrative booking analytics.

Justification for Inclusion

I selected this application for the database category because it provided an opportunity to move beyond basic CRUD behavior and design a more complete domain model around actual travel reservations.

The new booking model connects users and trips while also preserving selected values from the time a booking is created. This demonstrates the trade-off between normalized references and intentional duplication for historical integrity.

The schema includes validation and indexes based on the access patterns expected by the application. A dedicated booking repository isolates database interactions, while the service layer manages ownership rules, price calculations, booking creation, and application-level validation.

The enhancement also introduces a MongoDB aggregation pipeline that groups confirmed bookings by trip and calculates booking totals, traveler counts, revenue, and booking-date ranges. This transforms stored transactional data into information useful for administrative decision making.

Course Outcome Alignment

This enhancement most directly supports the outcome involving the use of well-founded computing techniques and tools to implement solutions that deliver value and accomplish industry-specific goals.

A travel application becomes substantially more realistic when it can manage reservations rather than only display trip information. The booking subsystem, customer history, and administrative reporting provide that additional value.

The enhancement also strongly supports the security outcome. Ownership checks, customer and administrator roles, administrator-only routes, controlled role assignment, and resource-level authorization help prevent authenticated users from accessing or modifying resources they do not own.

The aggregation report contributes to the outcome involving organizational decision making by converting reservation data into information that administrators can use to compare trip demand and estimated revenue.

Reflection

This enhancement reinforced that database development involves substantially more than defining fields and storing records. The most important decisions involved determining what should be referenced, what should be preserved historically, which indexes matched expected access patterns, and where authorization rules should be enforced.

One of the most important design choices was preserving the booking-time price. Referencing only the current trip record would have reduced duplicated values, but it would also allow later price changes to alter the apparent history of an existing reservation.

Resource ownership introduced another important distinction: authentication answers who a user is, while authorization determines what that user may access. A valid token alone is therefore insufficient to retrieve arbitrary booking records.

The aggregation pipeline also demonstrated how MongoDB can support analysis and reporting in addition to persistence. Grouping booking records at the database level avoids transferring every transaction to the client merely to calculate summary information.

The completed backend suite passed all ten automated tests with zero failures. Integration testing also confirmed that booking creation, customer ownership, administrator reporting, and role-based restrictions behaved as intended.

Overall, this enhancement transformed the database from a simple persistence layer into a more complete domain model supporting relationships, historical integrity, validation, authorization, indexing, and business reporting.
